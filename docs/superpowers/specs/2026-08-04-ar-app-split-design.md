## 1. 배경

발주처 요청 원문:

> AR 앱을 하나로 통합하여 개발할 경우 LH에서 요청한 'LH 전용 AR 앱' 개발이 이루어지지 않은 것으로
> 간주할 수 있으므로 개별 앱으로 개발해야 함.

즉 **계약상 요구는 "별도의 앱이 존재한다"** 는 사실 자체다. 기능 차이는 그 다음이다.

발주처가 제시한 기능 배분:

| 공통 기능 | 연구과제 앱 개별 | LH 전용 앱 개별 |
|---|---|---|
| 1. 시공현장 선택 | 1. 실시간 다자간 협업 | 1. 길이 측정 |
| 2. 3D 모델 선택 | 2. 오차 시각화 | 2. 철근 종류별 필터링 |
| 3. 3D 모델 렌더링 | | |
| 4. 3D 모델 미세조정 | | |
| 5. 3D 모델 투명도 조절 | | |
| 6. 화면 캡쳐 | | |

## 2. 확정된 결정

### 2.1 표는 "차별화 기능"만 나열한 것으로 해석한다

표에 없지만 현재 앱에 있는 **재고정(Visual Lock)** 과 **모델 삭제**는 **양쪽 앱 모두에 유지**한다.

재고정은 마커리스 방식에서 **유일한 드리프트 보정 수단**이다. 빼면 시간이 갈수록 모델이 실물에서
밀리고, 그 위에서 재는 길이 측정(LH)과 오차 시각화(연구과제)가 함께 틀어진다. 표의 목적은 두 앱을
구별하는 것이지 기반 기능을 걷어내라는 것이 아니라고 판단했다.

> 발주처에 확인할 수 있다면 **"연구과제 앱에서 길이 측정을 정말 제외하는 것이 맞는지"** 는 물어볼
> 가치가 있다. 이미 현장 검증까지 끝난 기능이다.

### 2.2 번들 ID는 현재 앱을 연구과제로 두고 LH 전용을 신규 등록한다

| | 연구과제 앱 | LH 전용 앱 |
|---|---|---|
| 타겟 | `LHRebarAR` (기존) | `LHRebarARLH` (신규) |
| 번들 ID | `kr.lh.rebar-ar` (기존) | `kr.lh.rebar-lh` |
| 표시명 | 철근 AR 연구 | LH 철근검측 |
| TestFlight 이력 | 빌드 32까지 유지 | 신규 |

번들 ID를 `kr.lh.rebar-ar.lh` 같은 **하위 형태로 두지 않는다**. CLAUDE.md 굳은살 #7 — ASC의
`filter[bundleId]`가 느슨한 접두사 매칭이라 하위 ID를 만들면 `scripts/build_status.py`가 두 앱을
섞어 본다. `kr.lh.rebar-lh`는 `kr.lh.rebar-ar`와 서로 접두사 관계가 아니다.

표시명은 발주처가 기기 홈 화면에서 보는 이름이므로 언제든 조정 가능하다.

### 2.3 이번 범위: 분할 + 신규 기능 2개

| 항목 | 이번 | 비고 |
|---|---|---|
| 앱 분할 (두 앱 빌드·배포) | ✅ | 발주처의 계약적 요구 |
| 3D 모델 투명도 조절 (공통) | — | **이미 구현돼 있음.** §4.1 참조 |
| 철근 종류별 필터링 (LH 전용) | ⚠️ 조건부 | §6 열린 항목 참조 |
| 오차 시각화 (연구과제) | ❌ 다음 작업 | 규모가 크고 별도 설계가 필요 |

즉 **이번 작업은 사실상 분할 하나**다. 발주처 표의 공통 기능 6개는 전부 이미 존재한다.

오차 시각화를 미루면 **LH 전용 앱은 표와 완전히 일치한 상태로 나가고**, 연구과제 앱만 나중에
채워진다. 발주처의 주된 우려(LH 전용 앱의 부재)가 완전한 형태로 해소된다.

## 3. 구조

### 3.1 타겟 두 개, 소스는 동일

`project.yml`에 타겟을 하나 더 만든다. **두 타겟 모두 같은 소스 목록을 포함**하고, 차이는 세 가지뿐이다:

- `PRODUCT_BUNDLE_IDENTIFIER`
- `CFBundleDisplayName`
- LH 전용 타겟에만 Swift 컴파일 플래그 `LH_ONLY`

LiveKit 패키지 의존성과 `NSMicrophoneUsageDescription`은 양쪽 모두 유지한다. 협업 코드를 LH 앱
바이너리에서 물리적으로 제거하는 방안(타겟별 소스 분리)도 검토했으나, **요구는 화면에서 보이지
않는 것**이므로 채택하지 않았다. 이 결정으로 `ARPlacementView.swift`(963줄)를 분해하지 않아도 된다.

### 3.2 기능 스위치

```swift
// LHRebarAR/App/AppFeatures.swift
enum AppFeatures {
    #if LH_ONLY
    static let liveShare  = false   // 실시간 다자간 협업
    static let measurement = true   // 길이 측정
    static let rebarFilter = true   // 철근 종류별 필터링
    #else
    static let liveShare  = true
    static let measurement = false
    static let rebarFilter = false
    #endif
}
```

`ARPlacementView`에서 해당 버튼·오버레이·시트를 `if AppFeatures.xxx`로 감싼다.

## 4. 신규 기능

### 4.1 3D 모델 투명도 조절 (공통) — **이미 구현돼 있음**

설계 초안에서 이 항목을 "신규"로 잡았으나, 코드를 확인한 결과 **이미 완전히 동작한다.**
PDF와 기억만 대조하고 소스를 확인하지 않아 생긴 오류이며, 이 절이 정정본이다.

현재 구현:

| 위치 | 역할 |
|---|---|
| `Placement/PlacementViewModel.swift:14` | `@Published var modelOpacity: Float = 0.7`, `didSet`에서 컨트롤러에 전달 |
| `AR/ModelAnchorController.swift:149` | `setOpacity(_:)` → `applyOpacity(_:to:)` |
| `AR/ModelAnchorController.swift:156` | 엔티티 트리를 순회하며 모든 `PhysicallyBasedMaterial`에 `.blending = .transparent(opacity:)` |
| `UI/Components/FineAdjustPad.swift:5,57,64` | 슬라이더 UI와 퍼센트 표시 |
| `UI/Screens/ARPlacementView.swift:190,244` | `FineAdjustPad`에 바인딩 전달 |

기본값이 **0.7**이라 배치 직후부터 이미 반투명이다.

**할 일 없음.** 다만 슬라이더가 **미세조정 패드 안에** 있어서, 발주처가 "투명도 조절이 어디
있느냐"고 물을 여지는 있다. 별도 상위 컨트롤로 빼는 것은 이번 범위 밖으로 두고, 기기 검증
체크리스트에 "양쪽 앱에서 투명도 조절이 동작하는지" 항목만 넣는다.

### 4.2 철근 종류별 필터링 (LH 전용) — 조건부

방향·레이어별로 철근을 켜고 끈다. 대시보드의 방향군 분류와 같은 개념이다.

**선행 확인 필요** — §6 열린 항목 1.

## 5. 릴리스와 검증

### 5.1 CI

`.github/workflows/ios-testflight.yml`을 두 타겟 모두 빌드할 수 있게 확장한다. 워크플로 입력으로
대상 앱을 선택한다(둘 다, 또는 하나만).

빌드 번호는 앱마다 독립이다. `scripts/next_build.py`가 ASC를 조회해 다음 번호를 정하므로,
번들 ID를 인자로 받도록 확장한다.

### 5.2 사용자가 해야 하는 단계

**App Store Connect에 새 앱 등록은 계정 소유자만 할 수 있다.** 다음은 사용자가 직접 해야 한다:

1. Apple Developer → Identifiers → 번들 ID `kr.lh.rebar-lh` 등록
2. App Store Connect → 새 앱 생성 (해당 번들 ID, 이름 "LH 철근검측")
3. 생성된 앱의 ASC App ID를 알려줄 것 (`scripts/build_status.py`용)

`scripts/build_status.py`는 이미 번들 ID **정확 일치**로 거르므로(굳은살 #7) 수정 없이 동작한다.

### 5.3 검증

시뮬레이터에는 ARKit이 없으므로 **기기 테스트가 필수**다. 두 앱을 같은 기기에 설치해 확인한다:

1. 두 앱이 홈 화면에 **각각 별도 아이콘**으로 존재한다
2. LH 앱: 공유 버튼이 **보이지 않고**, 측정 버튼이 보인다
3. 연구과제 앱: 측정 버튼이 **보이지 않고**, 공유 버튼이 보인다
4. 양쪽 모두: 미세조정 · 투명도 · 캡쳐 · 재고정 · 삭제가 동작한다
5. 투명도 슬라이더가 실제로 모델을 반투명하게 만든다
6. 두 앱이 같은 기기에서 **동시에 설치·실행**된다 (번들 ID 충돌 없음)

각 항목은 화면 캡처로 근거를 남긴다.

## 6. 열린 항목

### 1. 철근 종류별 필터링의 실현 가능성 — **착수 전 반드시 확인**

현재 앱은 USDZ를 **하나의 엔티티로 통째로** 올려 쓴다. 철근을 종류별로 끄려면 모델 안에서 철근이
**개별 노드/메시로 구분**돼 있어야 한다.

- BriconLab USDZ가 철근별로 노드가 나뉘어 있으면 → 그대로 구현 가능
- 통짜 메시면 → 앱에서는 불가능. 모델 생성 단계(BriconLab)에서 노드를 나눠 달라고 요청해야 한다

대시보드는 OBJ의 `o` 그룹명으로 철근을 갈랐지만 **그것은 다른 파일 형식**이므로 근거가 되지 않는다.

**확인 방법**: BriconLab에서 USDZ를 하나 받아 노드 구조를 덤프한다. 이 항목은 필터링 구현 태스크
직전에 사용자에게 다시 보고한다.

### 2. 오차 시각화 (연구과제 앱) — 다음 작업

대시보드의 분석 결과를 AR로 실물 위에 겹치는 기능. 별도 설계가 필요하다:

- 앱이 분석 결과를 어떻게 받는가 (대시보드 API? BriconLab 경유?)
- 결과의 좌표계(설계 모델 기준)를 AR의 배치된 모델 좌표계에 어떻게 대응시키는가
- 무엇을 보여주는가 — 판정 색(정상/허용초과/미시공/도면외)인가, 간격 편차 컨투어인가, 둘 다인가
